# meridian-roasters

A **React + Vite** single-page app scaffolded by
[KnowGitty Projects](https://knowhalim.com/knowgitty-projects). The whole page is
driven by `src/content.json` — you build a real, multi-section site by editing
that one file in the KnowGitty File Manager (or via the GPT/MCP tools). No code
changes required.

## Editing your content

`src/App.jsx` renders whatever it finds in `src/content.json`. The schema:

```json
{
  "title": "Site title (hero heading)",
  "tagline": "One-line intro under the title (optional)",
  "sections": [
    {
      "heading": "Section heading",
      "body": "One or more paragraphs. Separate paragraphs with a blank line.",
      "items": ["Optional bullet", "Another bullet"]
    }
  ],
  "footer": "Small text at the bottom (optional)"
}
```

Every field is optional and the page degrades gracefully:

- Add a section by appending an object to `sections`.
- Split `body` into paragraphs with a blank line between them.
- Add a bullet list with `items`; omit or empty it for no list.
- Drop `tagline` or `footer` entirely and that piece simply disappears.

You do **not** edit `App.jsx` to change copy — only `src/content.json`.

## Local development

```bash
npm install
npm run dev       # http://localhost:5173
npm run build     # production build to ./dist
npm run preview   # preview the build locally
```

## Deploy — GitHub Pages

This repo ships with `.github/workflows/deploy-pages.yml`. To turn it on:

1. On GitHub go to **Settings → Pages**.
2. Under **Build and deployment → Source**, choose **GitHub Actions** — NOT
   "Deploy from a branch". Use exactly ONE deployment source; never both, or they
   fight and you get stale or broken output.
3. Push to `main`. The workflow builds `dist/` and uploads it as the Pages
   artifact, then deploys it.

Builds take ~2–6 minutes. Watch the **Actions** tab before re-debugging — a
"broken" site is often just a build still in flight.

### The base path (why assets 404 on Pages)

GitHub Pages project sites serve at `https://<user>.github.io/<repo>/`, so every
JS/CSS/image URL must be prefixed with `/<repo>/`. The workflow does this for you
by setting `VITE_BASE=/<repo-name>/` in the build step, and `vite.config.js` reads
`process.env.VITE_BASE`. You should not need to touch it.

- **Custom domain or a user/org root site** (`<user>.github.io`): remove the
  `VITE_BASE` env from the workflow (or set it to `/`), so assets resolve at the
  domain root.
- **Local `npm run dev` / `npm run preview`**: `VITE_BASE` is unset, so base falls
  back to `/` and everything works locally.

### Lockfile & faster builds

This repo ships **without** `package-lock.json` (it must be generated by npm), so
the workflow uses `npm install`. After your first local `npm install`, commit the
generated `package-lock.json` — you may then switch the workflow to `npm ci` plus
`cache: npm` for faster, reproducible builds.

### SPA routing (later)

This template is a single page with no router. If you add client-side routing
later, plain history routes will 404 on refresh/deep-link on GitHub Pages (it only
serves one `index.html`). Use **hash routing** (`#/about`) or add a `404.html`
fallback that mirrors `index.html` so unknown paths still load the app.

### Debugging

If a deploy misbehaves, read **`TROUBLESHOOTING.md`** in this repo first — it maps
common symptoms (blank page, asset 404s, wrong content) to fixes.
